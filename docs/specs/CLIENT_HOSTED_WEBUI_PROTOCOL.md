# PixelLogic Client-Hosted WebUI Protocol

This is a draft protocol design note, not an implementation instruction.

The message names and envelope shape are design placeholders. They are not implemented and must not be treated as stable wire compatibility before a future handshake/status implementation prompt explicitly locks a first protocol version.

## Protocol Goals

- Let an authorized PixelLogic client host a local WebUI bridge.
- Preserve the existing WebUI API shape as much as possible.
- Keep the Minecraft server authoritative for graph, catalog, validation, runtime, trace, storage, and permissions.
- Make unauthorized clients harmless by default.
- Support revocation, expiry, stale request rejection, bounded payloads, and future tool/selection messages.

## Versioning

- protocol version: every message includes a protocol version or the session carries a negotiated version.
- compatibility: the server decides whether a client version is accepted, degraded, or rejected.
- mismatch handling: incompatible clients receive a user-readable error and no admin session.

Any first implemented version should be intentionally small. Avoid negotiating optional behavior that is not implemented yet.

## Message Types

### HELLO

Client -> server after joining.

Fields:

- `clientProtocolVersion`
- `modVersion`
- `supportedCapabilities`
- `webBridgeSupported`
- `toolUiSupported`

This does not authorize anything.

### HELLO_ACK

Server -> client.

Fields:

- `serverProtocolVersion`
- `compatible`
- `serverDisplayName`
- `reason` when incompatible

### START_ADMIN_SESSION

Server -> client after authorization.

Fields:

- `sessionId`
- `expiresAt`
- `allowedCapabilities`
- `oneTimeWebToken`
- `serverDisplayName`
- `protocolVersion`

### STOP_ADMIN_SESSION

Server -> client, or client -> server as a graceful stop.

Fields:

- `sessionId`
- `reason`

### SESSION_REVOKED

Server -> client when permission/session becomes invalid.

Fields:

- `sessionId`
- `reason`
- `closedAt`

### BRIDGE_REQUEST

Client -> server for a WebUI operation.

Carries a request envelope and one payload.

### BRIDGE_RESPONSE

Server -> client for successful or known application-level result envelopes.

### BRIDGE_ERROR

Server -> client for protocol-level failures that cannot be represented as a normal API payload.

### TOOL_ACTION

Client -> server for authorized tool item interactions. Requires `TOOL_ITEM_USE` plus a specific selection/action capability.

### SELECTION_UPDATE

Client -> server for authorized selection overlay updates. Requires the relevant selection capability.

## Request Envelope

- requestId: unique id generated by the client bridge for correlation.
- sessionId: active server-issued session id.
- capability: the capability required by this request.
- payloadType: stable operation id, for example `catalog.get`, `graph.get`, `graph.draft.save`, `simulation.run`, `tool.block.select`.
- payload: JSON payload for the operation, or a binary/chunk reference for future large payloads.
- graphVersion: graph fingerprint/version when mutating graph data.
- sequence: monotonically increasing per-session or per-graph save sequence.
- createdAt: client-created timestamp used for stale/replay checks.

The server must not trust client-provided capability; it should use the value as an intent and verify it against the active session.

## Response Envelope

- requestId: matches request.
- success: boolean.
- payload: operation result when successful or when returning a normal API error shape.
- errorCode: protocol or application error code.
- errorMessage: user-readable Chinese message where possible.

## Size / Chunking / Compression

### max payload size

Each message type should have a server-enforced size limit. Early versions can use conservative limits and reject large requests with `PAYLOAD_TOO_LARGE`.

### large graph transfer

Large graph documents may eventually need chunking:

- `transferId`;
- `chunkIndex`;
- `chunkCount`;
- `chunkHash`;
- total hash after reassembly;
- timeout for incomplete transfers.

Do not implement chunking until graph sizes require it, but reserve the protocol concept now.

### trace transfer

Trace responses should stay bounded. Prefer paging or latest-N windows instead of sending unbounded history.

### chunk ids

Chunk ids must be bound to the session id, request id, payload type, and expiry.

### timeouts

Requests, chunk transfers, and pending responses should expire. The bridge should surface a readable timeout message to the WebUI.

### compression

Compression can be added later for large graph payloads. It must be negotiated and size-checked after decompression to avoid zip-bomb style failures.

## Error Model

- unauthorized: no active session or missing capability.
- unsupported protocol: client/server version mismatch.
- expired session: session expired or player disconnected.
- invalid payload: payload failed schema or business validation.
- rate limited: request frequency exceeded server limits.
- stale graph: graph fingerprint/version/sequence no longer matches.
- internal error: unexpected server failure; should not leak stack traces to WebUI.

## WebUI Transport Mapping

### catalog

- `GET /api/pixellogic/catalog`
- bridge payloadType: `catalog.get`
- capability: `CATALOG_READ`

### graph

- `GET /api/pixellogic/graphs`
- `GET /api/pixellogic/graphs/{id}`
- `GET /api/pixellogic/graphs/{id}/draft`
- bridge payloadTypes: `graph.list`, `graph.get`, `graph.draft.get`
- capability: `GRAPH_READ`

### save/validate/commit

- `PUT /api/pixellogic/graphs/{id}/draft`
- `POST /api/pixellogic/graphs/{id}/validate`
- `POST /api/pixellogic/graphs/{id}/commit`
- bridge payloadTypes: `graph.draft.save`, `graph.draft.validate`, `graph.draft.commit`
- capabilities: `GRAPH_EDIT`, `GRAPH_COMMIT`

Draft save and commit should carry graph fingerprint/version and save sequence.

### simulation

- `POST /api/pixellogic/test/reset`
- `POST /api/pixellogic/test/start`
- future `POST graph.simulate`
- bridge payloadTypes: `simulation.reset`, `simulation.run`
- capability: `SIMULATION_RUN`

Reset should stay an internal helper behind user-facing "test run" where possible.

### trace

- `GET /api/pixellogic/traces/latest`
- `GET /api/pixellogic/traces`
- bridge payloadTypes: `trace.latest`, `trace.list`
- capability: `TRACE_READ`

### future runtime

- real server-side execution should be separate from simulation.
- bridge payloadType: `runtime.run`
- capability: `RUNTIME_RUN`
- requires stronger audit and safety gates.

## Security Rules

- Unauthorized clients can send payloads; the server rejects them.
- Never rely on client-side UI hiding for permission.
- Bind sessions to player UUID and current connection.
- Re-check capability on every request.
- Enforce request size and rate limits.
- Reject stale sequence and graph-version conflicts.
- Bind local WebUI token to session and expiry.
- Do not allow the local bridge to bind `0.0.0.0`.
- Do not allow wildcard CORS.
- Close bridge/session on disconnect, revoke, protocol mismatch, and timeout.
- Do not log one-time tokens or full bridge URLs.
